# 游戏与关卡的服务归属

角色、血条和关卡任务通常在切关卡后结束；语言设置和账号信息可能需要一直保留。事件总线该放哪里，取决于这些对象需要活多久。

## 两种寿命，同一种 EventBus

| 对象或通知 | 由谁管理 | 什么时候清理 |
| --- | --- | --- |
| 语言、账号等跨关卡通知的总线 | 游戏启动代码 | 游戏服务结束时 |
| 当前关卡的角色受伤、击杀等通知总线 | 关卡启动代码 | 离开关卡时 |
| 血条对生命值的监听 | 血条组件 | 关闭血条时 |
| 场景 UI 对全局语言变化的监听 | 这个 UI 组件 | UI 离场时，即使全局总线还在运行 |

“全局”和“关卡”指的是实例归谁持有，不是两套总线类型。组件只拿到自己需要的 EventBus 参数，不需要访问一个可查询所有服务的大型 Context。

## 模块如何获得服务

游戏启动代码先创建长寿服务；进入关卡时把需要的服务传给关卡启动代码。关卡启动代码创建关卡总线和角色，再把需要的实例交给血条、任务等对象。

普通 C# 对象通过构造参数接收依赖。Unity 组件通过明确的方法接收依赖；绑定之前不开始监听。Inspector 引用适合连接同一场景内的组件，跨场景依赖由启动代码传入，不在业务组件里 Find。

例如角色只需要关卡事件总线，就只传这一个参数，不把整个游戏入口或任意服务查询器传进去。语言模块可直接暴露自己的变化事件，没必要强制所有模块接入 EventBus。

## 退出关卡时的顺序

1. 停止接受新的关卡操作，暂停排队事件处理。
2. 请求关卡自己的后台任务取消，并保留观察完成与错误的方式。
3. 关闭界面和模块，释放它们对局部及全局事件的监听。
4. 关闭关卡总线，拒绝迟到投递，再卸载关卡对象。

全局总线继续存在。后台工作应保存开始时的关卡总线；不要完成后重新查询“当前关卡”，否则旧关卡结果可能误投递给新关卡。

取消请求不等于任务已完成；总线关闭也不等于场景异步卸载已完成。游戏退出流程若需要等待，必须由该项目的任务和场景管理代码明确处理。

## 启动失败时

只清理本次已经取得所有权的资源，不释放外部借来的服务。初始化到一半失败时，已创建的模块也要逐项清理；一个清理错误不能阻止其他资源退出。

游戏可以选择保留启动场景、常驻根对象等方式持有全局服务，Core 不强制场景布局。当前可复用接口只有 EventBus、Lifetime 和 EventBusHost；这里的“游戏启动代码”“关卡启动代码”表示项目职责，不是 Core 已提供的通用场景管理类。
