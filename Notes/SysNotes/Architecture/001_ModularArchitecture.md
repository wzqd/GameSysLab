# Core 与模块装配

## 决策

先实现 Core 事件分发与订阅生命周期实验，随后完成 Timer、Pooling、UI、本地化的最小版本，再考虑玩法系统。游戏与关卡的启动代码显式创建所需对象、传入依赖并负责清理。

> [!info] 状态
> 事件与生命周期模块已实现，31 项 EditMode 和 23 项 PlayMode 测试此前通过；带对照的 GC.Alloc 测量已完成。对象归属原则见 [[Architecture/002_游戏与关卡的服务归属]]。首个实验为 [[Experiments/001_CoreLifecycle]]，证据限当前 Windows 编辑器环境。

## 原因与替代方案

完全独立的脚本适合极小实验，但重复进入、失败清理和多个系统装配需要一致约定。完整通用框架会提前固定尚未验证的接口。因此以事件订阅的创建和释放验证生命周期，保留模块独立性。

Core 不引用具体系统；系统也不必强制依赖 Core。实例化事件工具放在 Core/Events，但使用仍可选；Timer、对象池、UI 和本地化保留独立边界，不强制依赖事件总线。

## 代价

装配代码需要手动维护，可能有少量重复。依赖、创建顺序和对象归属可以直接阅读。暂不具备自动发现依赖或运行期动态加载能力。

## 重新评估条件

- 资源清理已提取独立 Lifetime；只有实际出现多层拥有关系时，才重新评估作用域树。
- 出现真实异步资源需求：单独设计取消、失败恢复与卸载。
- 手写依赖顺序频繁出错且有证据：评估自动调度。
- 时间、随机性或存储阻碍测试：在使用边界引入可替换接口。

初期手动创建与连接对象，首版不做全局 Instance、通用服务查找、自动注册、Scope 树或 Command 总线。UI 使用轻量 MVP，其他模块不强制套同一模式。每次扩展记录使用者与验证结果，不因未来可能有用而增加公共层。

## Timer 交付增量

独立 Timer 已实现延迟、循环、暂停恢复重置、取消与 Unity 时间接入；Runtime 不引用 Core。全项目 55 项 EditMode、29 项 PlayMode 通过，测量与限制见 [[Experiments/002_Timer]]。下一步 Pooling。
