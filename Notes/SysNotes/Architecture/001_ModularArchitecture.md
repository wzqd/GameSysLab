# Core 与模块装配

## 决策

先实现小型 Core 生命周期实验，再逐步接入可选模块与玩法系统。每个 Demo 的 Bootstrap 显式创建所需对象、传入依赖并负责清理。

> [!info] 状态
> 架构方向已确定，代码与运行验证尚未完成。首个验证为 [[Experiments/001_CoreLifecycle]]。

## 原因与替代方案

完全独立的脚本适合极小实验，但重复进入、失败清理和多个系统装配需要一致约定。完整通用框架会提前固定尚未验证的接口。因此先解决生命周期这一具体问题，保留模块独立性。

Core 不引用具体系统；系统也不必强制依赖 Core。事件、对象池和存档是可选模块，常用不等于启动必需。

## 代价

装配代码需要手动维护，可能有少量重复。依赖、创建顺序和对象归属可以直接阅读。暂不具备自动发现依赖或运行期动态加载能力。

## 重新评估条件

- 多个 Demo 出现相同生命周期代码：提取小型公共实现。
- 出现真实异步资源需求：单独设计取消、失败恢复与卸载。
- 手写依赖顺序频繁出错且有证据：评估自动调度。
- 时间、随机性或存储阻碍测试：在使用边界引入可替换接口。

每次扩展记录使用者与验证结果，不因未来可能有用而增加公共层。
