# 角色受伤后，怎样通知血条

角色受到伤害时，角色自己扣血，然后发出“生命值已经变化”的通知。血条收到通知后刷新显示。角色不需要知道场景里有几个血条，也不需要引用 UI。

事件适合通知已经发生的事情。扣多少血、伤害是否有效，仍由角色逻辑决定；不要把扣血流程拆成一串事件。

## 先认识三个动作

| 想做什么 | 调哪个方法 | 什么时候发生 |
| --- | --- | --- |
| 血条开始关注角色生命值 | `Subscribe<HealthChanged>(...)` | 登记监听，以后收到同类型通知 |
| 角色扣血完成后通知血条 | `Publish(new HealthChanged(...))` | 现在执行监听，执行完才返回 |
| 希望稍后通知，或从后台提交结果 | `TryQueueEvent(...)` | 先入队，等主线程处理；返回 false 表示没排进去 |

一般的角色受伤使用 Publish 即可。排队不是后台执行监听，也不保证一定下一帧执行；实际由主线程何时调用 `ProcessQueuedEvents()` 决定。在 Unity 中通常交给 EventBusHost 每帧调用。

## 一个事件里放什么

事件记录接收者需要知道的数据。多个角色共用一条总线时，带上角色 ID，血条才能判断是不是自己的角色。

```csharp
using GameSysLab.Core.Events;

public readonly struct HealthChanged : IEvent
{
    public int CharacterId { get; }
    public int CurrentHealth { get; }
    public int MaxHealth { get; }

    public HealthChanged(int characterId, int currentHealth, int maxHealth)
    {
        CharacterId = characterId;
        CurrentHealth = currentHealth;
        MaxHealth = maxHealth;
    }
}
```

这是用于说明接入的业务类型，不是 Events 模块自带的事件。业务可以按需要定义金币变化、任务完成等类型。模块不保存当前生命值，不提供历史事件；血条刚打开时，先从角色读取当前血量，再订阅后续变化。

IEvent 是空标记，让读代码的人明确知道这是事件，并让总线拒绝直接发送 int、string 等非事件类型。不可变性仍由类型自己保证；不要在只读事件里放一个之后还会被修改的 List 或角色对象。普通领域对象无需实现 IEvent，只有发出的事件数据需要。

## 谁创建总线，谁拿到总线

游戏或关卡的启动代码创建一条 EventBus，把同一个实例交给角色和血条。角色和血条不要各自 new 一条，否则互相收不到消息，也不要自己到场景里 Find。

下面的独立方法展示整个流程。HealthChanged 使用上面的定义；`showHealth` 是调用方传入的刷新血条函数，`reportError` 是错误记录函数。Unity 中在主线程调用。

```csharp
using System;
using GameSysLab.Core.Events;
using GameSysLab.Core.Lifecycle;

public static class HealthEventExample
{
    public static void Run(Action<int, int> showHealth, Action<EventError> reportError)
    {
        using (var levelEvents = new EventBus(reportError))
        using (var healthBarSubscriptions = new Lifetime())
        {
            const int playerId = 1;
            healthBarSubscriptions.Add(levelEvents.Subscribe<HealthChanged>(change =>
            {
                if (change.CharacterId == playerId)
                    showHealth(change.CurrentHealth, change.MaxHealth);
            }));

            int health = 100;
            health -= 20;
            levelEvents.Publish(new HealthChanged(playerId, health, 100));
        }
        // 先解除血条订阅，再关闭本方法创建的总线。
    }
}
```

实际游戏中，创建、订阅、扣血和清理分别发生在启动、打开血条、受到伤害和退出时，不会像这个短例子一样在一个方法内结束。Unity 持续运行的接法见 [[Guides/Events/Unity中接入事件模块]]。

## 什么情况下需要排队

例如后台完成路径计算，希望主线程收到结果：工作线程只调用 `TryQueueEvent(result)`。成功为 true；容量满或总线已经关闭为 false，需要调用方决定记录、重试或放弃。结果里不要存放需要在后台访问的 Unity 对象。

另一个场景是监听收到事件后，还想发出后续事件。同一条总线的监听里不能再次 Publish，可以 TryQueueEvent，等下一轮处理。普通业务的必需步骤仍优先直接调用方法，不为了串流程而大量排队。

```csharp
// levelEvents 与 change 来自当前调用上下文。
bool queued = levelEvents.TryQueueEvent(change);
// queued 为 false 时处理失败；不要在主线程无限循环重试。
```

排队成功不等于已经送达；退出关卡会清空剩余队列。只处理本轮开始时已有的消息，本轮新加的留到下一轮。消息引用不复制，排进去后不要再修改数据。

## 监听怎么结束、出错怎么办

Subscribe 返回的句柄代表这一次监听；释放它就停止监听。把句柄加入血条自己的 Lifetime，在血条关闭时 Dispose。下一次打开创建新集合，见 [[Guides/Lifecycle/界面关闭时清理订阅]]。

默认某个监听抛异常后，其他监听继续执行，并通过创建总线时传入的 reportError 报告。监听必须同步、短小，不能传 async void。不要用优先级表达必须依次成功的业务操作。

完整参数和限制见 [[Reference/Events/EventBus]]。需要排错时主动调用 `GetDiagnosticsSnapshot()`，可以看到活动监听、队列数和错误数；该方法会分配快照，不必每帧调用。
